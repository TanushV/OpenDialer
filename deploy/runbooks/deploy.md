# Deploy one shared authority

1. Use an already-owned Linux host with encrypted persistent volumes, time synchronization, restricted SSH, a firewall and a tested off-host backup destination. No paid host is provisioned by the app. The declared shared reference is 2 vCPU/4 GiB across application and database, and it is not certified for load-path latency: on it, even two synchronized reps at one call per minute miss the selection and event-to-state targets, though correctness holds. Size a dedicated host (start with 4 vCPU for a small team, with the background worker on its own CPU share) and measure a capacity point on matching hardware before relying on it. The acceptance harness does this: `scripts/measure_completion.py --profile shared --reps <team size> --cadence <seconds between a rep's calls>` reports every latency gate, write conflicts and queue recovery. It refuses to run except against an inspected container reference (`OPENDIALER_REFERENCE_MANIFEST`, binding the runner and PostgreSQL limits, as EXECUTION_SPEC §17 describes) and a disposable PostgreSQL on 127.0.0.1:55439. Record the measured point with the deployment.
2. Copy `deploy/.env.example` to a protected path outside the checkout. Generate independent random PostgreSQL password, authority secret and one-time bootstrap token. Store recovery copies separately; losing the authority secret loses access to encrypted records. Set the DNS hostname. Do not commit this file or put secrets in shell history.
3. Run `docker compose --env-file /protected/opendialer.env -f deploy/compose.yml up -d --build`. The migration service completes before API/workers. PostgreSQL has no published host port; only Caddy exposes HTTP/HTTPS. Confirm DNS/TLS and `/health`. Inspect service status without printing environment/secret values.
4. Bootstrap once with `POST /v1/setup`, the `X-Bootstrap-Token` header and seller/campaign/admin details over HTTPS. Remove the bootstrap value from routine operator access afterwards; setup cannot initialize a second first workspace. The platform owner can create additional isolated workspaces explicitly.
5. In the desktop connect to the HTTPS server, sign in and configure provider/policy/registry/budget settings. Create users with individual incoming-only WebRTC credentials. Never share the carrier account master key with rep desktops.
6. Exercise backup/restore and signed events on permissioned test endpoints. Obtain traffic approval and certify actual media/callback/billing behavior before admitting production traffic. Unconfigured providers and missing legal evidence fail closed.

The API owns call-control maintenance, webhook recovery, live coaching and immediate post-call work. One background worker handles bounded preparation and statistical refresh/training. The default deployment runs maintenance without an optional profile. Raw conversation content remains only in the API process. Research concurrency, optional-job budgets, deadlines and the resource-limited background worker protect live work. Monitor queue age, uncertain commands, registry freshness, budget consumption, carrier errors and disk growth. Do not infer provider availability from an HTTP health response.

Each process owns separate reusable HTTP pools for call control (16 connections), live coaching (12) and optional background work (4). Authentication stays per request; provider cookies are not retained and redirects are not followed. These engineering limits prevent background socket exhaustion from filling the live pool; they are not a certified rep-count capacity. Shutdown cancels workers before closing transports. Research fetching keeps its separate restricted transport.

For local container acceptance only, bind the API port to 127.0.0.1 and use synthetic credentials. `OPENDIALER_SIMULATION=true` is an explicit test override; production Compose defaults false. The reset-based pytest database is always separate from a running acceptance server.

## Local authority with an existing SSH host

Use this recipe only with a hostname and SSH host you already control. It creates no hosting account, subscription, or carrier fallback. The Mac/Windows desktop uses the OS SSH client; install/host-key setup remains the operator's responsibility if SSH is absent. The authority selects a new loopback port each launch, which the desktop passes to its owned SSH child. Do not configure the development port as the installed target.

1. On the forwarding host, dedicate an SSH user/key to this workspace. Restrict its server configuration to remote forwarding, `GatewayPorts no`, and `PermitListen 127.0.0.1:18765`; disable agent/X11 forwarding and interactive shell use where your SSH account configuration supports it. Verify the host-key fingerprint by your existing trusted channel and accept that key in the rep's OS SSH known-hosts store. `StrictHostKeyChecking=yes` and `BatchMode=yes` are enforced; the app will not bypass prompts or install keys. Keep the private key in the existing OS agent or standard protected SSH identity location. Do not put provider keys on this host.
2. Reserve remote loopback port18765 for this one authority. Confirm no other service owns it. Give another workspace a distinct port and hostname; never kill an existing listener to make the forward work.
3. Point an owned DNS hostname at this host, permit inbound443 (and80 if used for Caddy certificate issuance), and run Caddy on the same host using **`deploy/Caddyfile.local-ingress`**, not the connected full-API Caddyfile. Set `OPENDIALER_INGRESS_DOMAIN` to the bare hostname and `OPENDIALER_FORWARD_PORT=18765`. Run `caddy validate --config /protected/Caddyfile.local-ingress --adapter caddyfile` before applying it. Preserve your other Caddy sites. Keep the forwarding port loopback-only and administration/private database ports unexposed.
4. Open the actual local workspace in the installed app as its administrator. In Settings → Providers → Existing SSH forwarding host, enter host, user and remote port, enable, and save. Simulation and a connected authority cannot enable this local forward. The supervisor checks local backend health, starts only the OS SSH executable, and reports missing SSH or unavailable host/forward. It retries at1/2/4/8/16/30seconds, then at30seconds; disable stops its owned child. Switching authority, quitting and updating stop and reap only app-owned children.
5. Save `https://<owned-hostname>/webhooks/telnyx` as the public webhook URL along with the Telnyx public verification key and account configuration. Configure the same URL on the existing carrier application. Click **Check saved ingress**. It creates a one-use60second challenge, performs a bounded HTTPS proof, and separately checks signed-handler fixtures. These are software routing proofs; last real signed carrier event remains a separate field.
6. Verify from outside the host that `/health`, `/v1/workspace`, `/v1/admin/settings`, wrong methods and other paths return404. Only signed `POST /webhooks/telnyx` and exact `GET /webhooks/ingress-check/<32 lowercase hex>` reach the local authority. An inactive/expired nonce returns404 at the authority. A routed webhook still must pass signature/replay checks. Never broaden the proxy to all paths to resolve a failed check.
7. Test disconnect/reconnect and relaunch: the public hostname/remote port remain stable, the local port changes, and a fresh route proof succeeds. A changed saved public URL invalidates the old proof. Failure, sleep or quit prevents local events/preparation until the same authority resumes; pending work reconciles on restart without inventing missing speech.

An offline laptop cannot run Call Control callback routing. Use an account-proven compatible fallback already owned by the business, or the same authority in connected mode on an already-owned always-on host. No SIP-forwarding subscription is enabled. `offline_callback: unavailable` is an intentional deployment limitation until actual account evidence exists; a successful nonce is not offline callback proof.

The executable proxy acceptance uses a disposable, loopback-published Caddy container and a sentinel upstream, exercising allowed and denied paths/methods. It does not certify your DNS, TLS, SSH host or carrier account. Current recipe semantics follow [Caddy request matchers](https://caddyserver.com/docs/caddyfile/matchers) and [mutually exclusive handle blocks](https://caddyserver.com/docs/caddyfile/directives/handle).
