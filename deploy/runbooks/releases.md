# Release and update

Keep the stable identifier `com.opendialer.desktop`. Bump Python, desktop package/lock, Cargo/lock and Tauri versions together. Complete the acceptance matrix and preserve an installed baseline with a human note and suppression. Freeze both sidecars with `scripts/build_sidecar.py`: the local authority `opendialer-backend-<triple>` and the CPU trainer `opendialer-trainer-<triple>`, both listed in `bundle.externalBin`. The release must not contain a shell wrapper or depend on a source checkout/Python installation.

The authority runs local mode on SQLite only and serves promoted models with the pure-Python evaluator in `app/ml/serving.py`, so it ships without NumPy, SciPy, scikit-learn, joblib, the PostgreSQL drivers, the phone geocoding/carrier/time-zone tables, optional native accelerators (uvloop, httptools, watchfiles, websocket/markupsafe/YAML speedups, charset_normalizer) or SQLAlchemy's Cython builds (their pure-Python sources ship instead). A onefile sidecar re-extracts its native libraries on every launch and macOS verifies each freshly written image on first load (about 0.2 s each), so the number of native images loaded at startup, not the payload size, sets cold start; check new dependencies against that. Fitting runs only in the trainer: the authority launches the `opendialer-trainer` installed beside it (same triple/`.exe` suffix) as its bounded training child, and refuses connected mode when frozen (connected mode is the server image). A trainer run pays its own extraction and first-load verification of about 150 native images (roughly 30–45 s on a loaded Mac) inside the 300-second training bound. Model artifacts are JSON (`challenger.json`); artifacts from earlier releases (`challenger.joblib`) are never unpickled and report `model_format_retired: retrain` until the seller trains again.

On macOS, finish with `uv run python scripts/package_macos.py --build` after freezing. It gives only the two frozen Python sidecars the documented library-validation exception, re-seals the main bundle without broadening its entitlements, probes the signed backend (`--help`) and trainer (`--self-check`), verifies that the extracted update archive carries exactly both sealed sidecars, recreates the archive/DMG and signs the final bytes with their version. Running `tauri build` alone is not the final macOS release step.

Keep `TAURI_SIGNING_PRIVATE_KEY` and its password outside Git. The repository Actions secret store is configured; the pinned public key is in Tauri config. Build native packages on the corresponding OS. `.app.tar.gz.sig`/Windows/Linux signatures and the updater JSON must refer to the exact uploaded bytes. Publish a reviewed release only after verification; draft CI packages do not update users. The configured latest endpoint requires a published non-prerelease release. Developer previews must clearly disclose missing platform/provider certification.

For macOS public distribution, configure a real Apple Developer ID certificate, hardened runtime entitlements and notarization credentials, then validate a quarantined clean install. Updater integrity signing is separate from Apple trust. Windows publisher signing and actual Mac/Windows hardware acceptance have independent gates. Linux is not an advertised distribution target. Never claim these are passed because compilation succeeds.

Install once. Thereafter use Settings → App updates, verify the signed offered version, install it in place, quit/reopen, and check the saved workspace IDs, human note, suppressions, database integrity and new version. A failed signature must not replace the app. Do not uninstall/reinstall or reset data for an update.

Release artifacts include checksums, dependency notices, source revision and the acceptance report. Dependency/security CI, code review and reproducible test output accompany each release. Preserve updater key recovery material securely; losing it requires a separately planned trusted rotation, not silently changing the public key.

Windows upgrades must stop the owned frozen runtime before replacing its executable. In the locked tauri-plugin-updater 2.14.0, the updater built for the app (including the JavaScript install command) registers an `on_before_exit` hook that calls Tauri `cleanup_before_exit`; on Windows it runs that hook for both NSIS and MSI before launching the installer and calling `process::exit(0)`, without a `RunEvent::Exit`. The 0.3.0 desktop therefore registers its runtime cleanup as a resource drop guard as well as a normal exit handler. That cleanup stops and reaps the owned SSH child and its process group, terminates the sidecar's job object (process group on Unix) and waits for the launcher process, then waits up to 10 seconds until the installed `opendialer-backend.exe` and `opendialer-trainer.exe` can be opened exclusively (a training child is a member of the authority's job object), so the MSI path, which has no installer hook, does not race a terminating backend. A desktop crash does not orphan the authority: it receives its secrets as one JSON line on a private stdin pipe and exits when that pipe closes. The per-launch token and data key are never passed in the sidecar environment. An update from an installed 0.2.1 runs 0.2.1's own cleanup, which kills without the exclusive-open wait; the NSIS hook below covers that route, and an MSI update from 0.2.1 needs its own native evidence before MSI is advertised. NSIS preinstall also handles older releases: its embedded script selects only the canonical installed opendialer-backend.exe and opendialer-trainer.exe paths, stops those processes, and requires exclusive access before copying. It never deletes application data or kills unrelated executables. The path-isolation PowerShell test and a real signed 0.2.1→0.3.0 baseline upgrade are required; seeing the new desktop executable version alone is insufficient. Preflight must report the new backend version too.

For large Windows artifacts, stage-windows-release.yml can verify and upload the exact successful native build directly to an existing draft. It checks immutable run/source identity, pinned-key signatures, authenticated version, deliberate tamper rejection and saved native acceptance. Reconcile uploaded SHA-256 digests before publishing. This job never rebuilds or publishes a release. Use windows-acceptance.yml with baseline_version to exercise the existing published baseline through the signed updater.

Windows update installation is asynchronous. The acceptance harness must await the scoped updater process exiting and require the installed backend SHA-256 to match the backend extracted from the exact verified NSIS package before relaunching. Use the runner's PowerShell 7 for the completion probe and fail immediately on probe errors. A new GUI ProductVersion alone can appear while backend files are still being copied. Then require actual backend-version preflight, exact saved IDs, the human note and suppression continuity.

## 0.3.0 candidate acceptance order

E13 must pass before product freeze. Record the exact source, dependency locks, both full database coverage receipts, browser/native checks, mutation and independent review, and elapsed resource/load results. Do not carry old 0.2.1 receipts forward. Keep the installed app untouched while testing a protected, authenticated copy of its store. Preserve IDs, note hashes, denials, tasks, sessions and original effect identities.

Run `scripts/frozen_acceptance.py --expected-version 0.3.0 --output <protected-receipt>` against each actual packaged backend using `OPENDIALER_TEST_BINARY`; it finds the trainer beside that binary (or `OPENDIALER_TEST_TRAINER`). Its child PATH is empty, its cwd/data are fresh, and it waits twelve real minutes for the rolling expiry journey. It exercises the callback and human note, original-session restart, projection and a real temporary training child through the packaged trainer, which must fit and export a servable human stage. Source tests with an injected clock certify the harness only. Pass signature/version/tamper and fresh-install checks for both NSIS and MSI if both remain advertised.

The installed updater is pinned to GitHub's public latest manifest and cannot consume a draft. Stage both verified packages, then publish a controlled validation release labeled **installed-update validation in progress**. Immediately exercise the existing 0.2.1 signed updater on Windows and Mac; wait for installer exit and exact accepted backend bytes, then verify native UI, retained data/session and local/shared journeys. Only after both pass change release metadata to accepted. If product bytes fail, withdraw the candidate/restore the prior public latest, preserve the failed installation for diagnosis and use a new patch version for changed bytes. A harness-only fix reuses the accepted packages. Never reinstall or erase a workspace to repair an update.
