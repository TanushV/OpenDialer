The end goals that govern the work

The product is a calling workspace that helps a seller reach the right people and convert useful conversations. It should make continuous calling easier, while the rep owns the conversation and books meetings. The latest accepted requirements override the older Gong-style integration and recording scope.

Why the work became larger without becoming complete

The sequencing was wrong. Individual counterexamples led to worthwhile fixes, but each fix was often followed by another supporting surface, recovery edge or configuration slice before the entire seller journey was closed. Tests-first was useful, but passing focused tests was allowed to drive the work queue more than the final product contract. Consolidation and deletion of superseded paths were deferred.

There are 246 commits after the audited baseline at the reviewed HEAD. That is evidence of incremental work, not evidence of completion. The plan correctly leaves M1–M9 partially open, while the detailed log contains many green subsets. Repeating subset counts without the parent-milestone status makes progress hard to interpret.

The repeated check that no new dependency, service or table was added measured only infrastructure growth. Application complexity can still grow through overlapping calculations, implicit shared state, duplicated validation, extra UI states and recovery branches. The source and large functions have grown substantially despite the smaller deployment.

Some growth is necessary: original event loss, duplicate paid actions, privacy leakage and destroyed human notes require real handling. Removing those guarantees would create a smaller but unreliable app. The correction is to reuse coherent state and decisions, remove parallel implementations and verify the entire workflow before adding more supporting detail.

The architecture problems that matter

1. One large implicit service remains behind the smaller files

Dialer directly inherits 12 classes; its Application ancestor inherits preparation, live help, privacy, accounting and the base service, which itself inherits reservation planning. Methods across these files call through the same object and share database, raw buffer, provider clients, queues and caches. File splitting improved navigation but did not establish small explicit data contracts.

Fix: retain the existing facade and routes for compatibility. Move decision logic to functions taking explicit snapshots, with a short I/O coordinator at each workflow boundary. Extract only real separations encountered while consolidating the core journeys. Avoid a new dependency-injection framework, service fleet or blanket class rewrite.

Source: Dialer inheritance, Application inheritance, base service.

2. Two capacity forecasts answer different questions

Without explicit staffed windows, capacity_forecast estimates multiple retries using the policy's minimum retry interval. With staffed windows, it delegates to a planner that places one next due attempt per lead using time, staff, ownership and DID constraints. Adding a staffing schedule therefore changes both the constraints and the meaning of demand. The time planner's objective prioritizes callbacks and attempt count; it is not yet the learned conversion optimizer described in the plan.

Fix: normalize simple declared availability into the same slot input as named staffing, then use one feasibility engine. Separate known next attempts from estimated future retries. Introduce pooled retry demand and measured work estimates with uncertainty; preserve callbacks and stable identity. Compute existing-only capacity and the incremental value of additions from the same inputs. Remove the aggregate branch once compatibility fixtures cover the unified behavior. Keep exhaustive tiny-case checks and bounded heuristics; no new solver is justified yet.

Source: forecast switch and aggregate demand, time forecast, current caller-ID selection.

3. Cached reports still depend on expensive historical rebuilds

Dashboard GETs are improved: they read saved reports. Rebuilding those reports still loads historical calls, leads, events, advice, feedback, assignments and decisions. Many seller-level writes invalidate the same report generation, including call and coaching metadata. A long rebuild can be superseded by ordinary activity.

refresh_optimization additionally loops through inventory and leads inside a write transaction, repeatedly searches cached scheduling-plan lists and calculates future slots. Transaction-local caching reduces SQL, but repeated Python searches remain proportional to the growing list and can approach quadratic comparison work. Moving a computation into a background job does not make its lock occupancy or CPU cost disappear.

Fix: update small outcome/day/number aggregates from finalized events and corrections. Keep one explicit replay/rebuild route. Use indexed identities or maps for existing plans; calculate decisions outside writes and persist short validated batches. Invalidate the smallest relevant projection instead of rebuilding everything after every unrelated source change. Share metric definitions across home, optimization and exports.

Source: projection invalidation, historical report, optimization refresh, home aggregation.

4. Freeform help exists, but its meaning guard is still wrong

The previous five-topic interpreter and exact-sentence restriction have been removed. However, the current validator still tests factual-looking sentences by word overlap, exempts many questions, and does not apply the same semantic test to the explanation. Knowledge stating that the product is not compatible with offline use can allow the opposite assertion. A false premise can pass as a question. A valid browser-access paraphrase can be rejected.

The latest test file has nine failing cases and two passing cases. These include both concrete validation counterexamples and unimplemented selective-review/accounting contracts; they are not nine independent live-provider failures.

Fix: replace lexical truth tests with a compact evidence/source contract and selective model-assisted review for novel material assertions. Keep benign contextual questions on one inference. Review the displayed explanation as well as the primary answer; do not stream an unreviewed claim early. An unsupported answer should acknowledge the missing fact or ask a useful clarification. Every extra submitted request must share deadline, privacy, source-version and cost accounting. Model review is fallible and needs adversarial/human evaluation; it is not mathematical proof.

Source: current validator, committed counterexamples. No semantic product fix was made during this audit.

5. Live memory and post-call interpretation are not one complete path

The live helper already retains bounded paraphrased rundown points, needs and questions. The basic analysis builder can use them. But analyze_postcall sends only still-live transcript chunks to its separate extraction model, then requests a separate meaning review and replaces summary/problem/objection fields with that output. It does not send the earlier call_memory returned by the initial read. This is a source-demonstrated risk of losing earlier context in the final rundown; it was not freshly reproduced by a runtime test in this audit. Existing commitment handling has explicit preservation rules, so it would be inaccurate to say every old task is deleted.

Full post-call extraction also uses the separately configured inference adapter and privacy setting; an OpenRouter key alone does not configure that path.

Fix: make one bounded conversation state the input/output of incremental interpretation and finalization. At meaningful stable chunks, update advice, needs, unresolved questions, commitments, observations and rubric accumulators together. At hangup, finalize that state with recent chunks and the rep's outcome. Keep source IDs/revisions and interpretation coverage; never pretend expired unprocessed evidence was analyzed. Select stronger review only for ambiguity/material assertions. Preserve human edits and task identities. A second historical transcript pipeline is unnecessary.

Source: analysis and call memory, post-call request/publication, provider-role configuration.

6. Preparation has real batching, but research and throughput need closure

Ordinary preparation iterates leads serially within a work unit; the runner permits two concurrent preparation jobs per lane. That is bounded concurrent batching, not a single model call for twenty leads. A separate deferred Batch route exists. The normal research path fetches the company homepage only, despite the planned bounded discovery of useful first-party pages.

Fix: keep the current queue, company cache, per-lead identities and partial retry. Fetch only a few relevant permitted pages when the homepage lacks needed facts. Measure prepared-call runway and provider throughput before increasing concurrency. Group shared company research, use supported provider Batch where lead time permits, and prioritize tomorrow's due work. Do not introduce a browser fleet or live research.

Source: ordinary work unit, company research, bounded runner.

7. Setup diagnostics still disagree with the actual DNC path

Source inspection found that preflight requires a published national snapshot, while per-attempt authorization can also use a fresh authorized prepaid result. A prepaid-only workspace can therefore receive a snapshot-missing diagnostic despite having a different supported screening path. This is a source-level finding awaiting its own regression, not a newly executed test result.

Fix: use the same capability/coverage definition for setup and actual authorization. Distinguish configured provider access, screened leads, stale/missing coverage and the per-attempt decision. Background screening/refresh should prepare the queue within its budget; opening settings must not spend credits.

Source: preflight snapshot requirement, prepaid authorization alternative.

8. Native delivery is a distinct unfinished product step

The installed app is still 0.2.1. Current source changes do not appear in that binary automatically. Earlier Mac/Windows receipts apply to the historical release; they cannot certify the current Python child process, privacy migration, new screens or updated runtime. A source push is not an update delivery.

Fix: finish integrated acceptance, freeze one product revision, test migrations on protected copies, build both platforms and verify signed artifacts. Apply the real updater, prove data/session continuity, and test the installed app. Windows must finish the scoped updater and match the accepted backend hash before relaunch. Do not reinstall.

What statistical ML should do, and what should stay deterministic

Real learning exists. The current pooled model estimates human answer, right-party connection and conversion from observed outcomes with smoothing. A trained challenger uses calibrated histogram gradient boosting. Outcome-time boundaries, model loading and serving have received substantial repairs. The current tabular input still has a narrow fixed feature set, including eight hashed segment buckets; conversation observations are used for descriptive associations/context, not yet a validated general conversation-informed predictor.

Starting without thousands of manually labeled calls is feasible. Initially the app can honor callbacks and calling windows, distribute capacity, preserve coverage and use pooled estimates with visible uncertainty. Carrier events and rep-confirmed outcomes supply much of the training signal. LLM interpretations can add provisional concepts; they should not fabricate attendance, sales or right-party identity.

Remaining learning work: define versioned prior-call features available before each decision; distinguish absence from missing interpretation; normalize concepts without a five-topic taxonomy; evaluate incremental predictive value on later grouped periods; use support and uncertainty; keep control/rollback. Test finite strategies rather than pretending every generated sentence has a known selection probability. Observational correlations may inform context, but do not establish causal conversion improvement.

Health currently mixes observed statistics with fixed engineering intervention thresholds. These need one visible policy with evidence and hysteresis. A local failure/pickup estimate must never be labeled a carrier spam-screen result. Number choice still primarily follows binding, regional/general preference, load and health; it has not yet become the full learned joint optimizer.

Source: pooled funnel, challenger features, conversation associations, observed health.

Cost conflicts that code cannot remove

A prepaid DNC API is available: the reviewed vendor currently lists $100 for 60,000 queries with no recurring charge and no credit expiry. That is an access method and pricing offer, not proof that every seller has the required registry authorization. FTC guidance describes seller-specific access/SANs, five no-fee area codes and separate treatment for qualifying exempt organizations. The user's requirement to screen every US destination remains; the application must not infer an exemption to bypass it. Vendor pricing · FTC source.

Telnyx reputation monitoring currently has a $100 monthly enterprise fee plus usage. It remains excluded. Observed Telnyx events/CDRs can support useful health checks without that subscription, but cannot prove how every destination carrier labels the number. There is no verified all-carrier PAYG replacement in this acceptance baseline. Telnyx pricing.

Under the accepted no-new-recurring policy, additional-number proposals are informational and purchases remain blocked. Existing rentals remain disclosed. If the list cannot be covered with existing inventory, show the shortfall and schedule tradeoff rather than pretending a new rented DID is a one-time PAYG charge. No paid provider requests or account changes were made in this audit.

The simpler target inside the existing stack

Import & screen→Prepare ahead→Choose allowed work→Call with live help→Confirm rundown & next action→Learn & refresh brief
  1. One prospect state. Keep authoritative identity, permission, outcomes, task/hold and a bounded derived brief. Raw speech remains ephemeral. Human edits and model interpretations retain distinct provenance.
  2. One conversation interpretation path. The background helper updates compact state and optional advice in the same ordinary inference. Finalization uses that state. Stronger review is selective and separately costed.
  3. One schedule/capacity calculation. Normalize availability, apply policy/identity constraints, use pooled predictions and account for existing obligations. Reservation and forecasts share the same meanings and feasibility primitives.
  4. One outcome/metric aggregation path. Update small aggregates from real events; replay corrections explicitly. Avoid recreating the whole dataset for ordinary dashboards or every candidate.
  5. One small runtime and existing durable boundaries. Reuse inbox, external-effect outbox and job queue for their different responsibilities. Shared lease/accounting helpers stay small. No agent framework, queue service, vector service or language migration.
  6. One ordinary rep surface. Prepared script, fixed help, relevant numeric context, controls and wrap-up. Put diagnostics, model trials, billing recovery and configuration in advanced/admin views.

A full rewrite would discard working recovery and migration behavior and recreate many of the same risks. Consolidation should remove an old path in the same accepted change that replaces it, after tests prove equivalent authorized behavior. Simplicity is measured by fewer competing definitions, bounded work and easier complete journeys—not by deleting arbitrary lines.
